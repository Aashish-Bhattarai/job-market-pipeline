# Job-market pipeline — shared contracts

Root: this repository (below: `pipeline/` means the repo root).
Python 3.13 (`python`), stdlib + `openpyxl`, `pyyaml`, `python-docx`, `requests` (pip install if missing).

## Non-negotiable
Every CV line and cover-letter sentence must be defensible **solely from `profile/facts.yaml`**.
Nothing may add a skill, tool, employer, metric, or claim that is not in a fact.

## 1. `profile/facts.yaml` (owner: FactsBank)
Personal, gitignored -- copy `profile/facts.example.yaml` and fill in your own facts.
```yaml
contact: {name, email, phone, linkedin, github}
education:      [{id, degree, institution, location, dates, details: [str]}]
certifications: [{id, name, year}]
skills:         {<group>: [str]}        # only skills evidenced in the CV
experience:
  - id: example-co                       # short slug
    org: Example Tech Ltd
    role: Junior Application Developer
    location: "Remote, UK"
    dates: "June 2026 – Present"
    employment: part-time | partnership | full-time | contract
    facts:
      - id: example-co.doc-intel         # <experience id>.<slug>, unique
        text: "Built a document intelligence application ..."
        tags: [python, ocr, llm, ...]    # lowercase keywords for matching
        source: cv | chat-2026-09-26
projects: same shape as experience (org optional)
```

## 2. `profile/answers.yaml` (owner: FactsBank)
Personal, gitignored -- copy `profile/answers.example.yaml` and fill in your own answers.
Standing form answers: contact, addresses (`default`, `sussex`), address rule
(Sussex jobs → `sussex`, else `default`), right_to_work, sponsorship_now,
sponsorship_future, visa (status/expiry — only when a field explicitly asks),
notice_period, salary rules (a threshold + two bands), protected_characteristics
(preference, gender), criminal_convictions, background_check, relocation,
years_experience (a stated number per skill; anything else → derive from facts
or queue).

## 3a. Per-job archive — `pipeline/out/<job_id>/` (generated view, kept forever)
The database (`pipeline/ledger/`, below) is the source of truth; `pipeline/out/<job_id>/` is a
human-browsable copy written alongside it, not a separate record:
- `job.json` — snapshot of the posting at apply time: job_id, company, title, location, region,
  url, apply_url, ats, posted_at, description, fit decision, applied_at, submitted (bool).
- `selection.json`, `cover.json`, `defensibility.json` — tailoring inputs/outputs (below).
- `CV_<name>.pdf` / `.docx` and `Cover_Letter_<name>.pdf` / `.docx` / `.txt`
  — the exact files uploaded, named from `facts.yaml`'s `contact.name`. Uploaded filenames stay
  clean (no job id in them); the folder carries the id.
- `ANSWERS.md` — every field asked and every answer given, across every application attempt for
  this job, with its source and a link to the screenshot. Regenerated by `pipeline/run/views.py`
  from the ledger; never hand-edited.
Every one of these files is also stored content-addressed under `pipeline/store/` and recorded as
a `documents` row (CV/cover/selection/etc.) or inside an `applications`/`form_answers` row
(the actual submission and every field value) — see §8. `jobs.db` stores `cv_path`/`cover_path`.

## 3. Tailoring selection — `pipeline/out/<job_id>/selection.json`
```json
{"job_id": "...", "headline": "Machine Learning and AI Engineer",
 "summary": {"text": "...", "fact_ids": ["..."]},
 "skills": {"<group>": ["..."]},
 "experience": [{"id": "example-co", "fact_ids": ["example-co.doc-intel", "..."]}],
 "projects":   [{"id": "fieldtrust", "fact_ids": ["..."]}],
 "education_ids": ["..."], "certification_ids": ["..."]}
```
Cover letter — `pipeline/out/<job_id>/cover.json`:
`{"job_id": "...", "company": "...", "role": "...", "paragraphs": [{"text": "...", "fact_ids": ["..."]}]}`

## 4. Renderers (owner: CvRenderer)
`python pipeline/render/render_cv.py <selection.json> <out_dir>` → `CV_<name>.docx` + `.pdf`
`python pipeline/render/render_cover.py <cover.json> <out_dir>` → `Cover_Letter_<name>.docx` + `.pdf` + `.txt`
`python pipeline/render/validate.py <selection.json|cover.json>` → exit 0 if every fact_id exists and
every CV bullet is a fact text verbatim; non-zero with reasons otherwise.
ATS-friendly: single column, no tables/text boxes/images/headers-footers for content, standard
section headings, standard fonts.

## 5. Normalized job (all discovery sources return a list of these dicts)
```python
{"source": "greenhouse|lever|ashby|workable|smartrecruiters|himalayas|jobsacuk|gradcracker|hiringcafe|wttj|linkedin|reed|hnhiring",
 "company": str, "title": str, "location": str, "remote": bool | None,
 "url": str,            # posting page
 "apply_url": str | None,
 "ats": str | None,     # greenhouse|lever|ashby|workable|smartrecruiters|workday|icims|other

```
Source modules: `pipeline/discover/sources/<name>.py` exposing `fetch(config: dict) -> list[dict]`.

`- {name, ats, slug, careers_url, region: london|sussex|remote}`.

## 6. `pipeline/data/jobs.db` (SQLite, owner: DiscoveryCore; also carries the ledger, §8)
Table `jobs`: `id TEXT PK` (sha1 of canonical url), all normalized fields, `discovered_at`,
`status` (new | filtered_out | fit_pass | fit_fail | queued_account | tailored | needs_review |
ready | approved | queued_manual | applied | skipped), `reason`, `fit_score` REAL, `fit_json`,
`cv_path`, `cover_path`, `applied_at`, `notes`.
Dedupe/exclusion inputs: an optional `exclude_companies.txt`, `pipeline/data/linkedin_applied.csv`,
a configurable scam-list, max 2 applications per company per 30 days (enforced at both
`filter.py` and the apply step).

## 7. `pipeline/data/linkedin_applied.csv` (owner: LinkedInImport, optional)
Columns: `company,title,location,applied_when,linkedin_status,job_url`. Feeds `import_linkedin.py`
and the exclusion list above; not required to run the pipeline.

## 8. Ledger (owner: integrator; `pipeline/ledger/`) — absolute traceability
Every evidential write goes through here, never only to a loose file. Full schema:
`pipeline/ledger/schema.py`. API: `pipeline/ledger/core.py` (`connect`, `tx`, `record`,
`append_event`, `store_bytes`/`store_file` — content-addressed under `pipeline/store/`,
`profile_version`, `verify`), `pipeline/ledger/bank.py` (answer bank + question queue),
`pipeline/ledger/llm.py` (headless model calls via `omp -p --mode json`, see below),
`pipeline/ledger/orders.py` (builds an apply work order from the latest documents + bank export).
- **Append-only, hash-chained.** `profile_versions`, `blobs`, `llm_calls`, `requirements`,
  `documents`, `applications`, `form_answers`, `answer_aliases` reject UPDATE/DELETE at the SQL
  level (triggers); a changed answer is a new `answer_bank` row that supersedes the old one, never
  an edit. Every attested row is paired with an `events` row carrying its hash;
  `events.hash = sha256(prev_hash + ts + actor + job_id + type + payload)`, so any edited,
  deleted, or out-of-band row is detectable. `python pipeline/run/verify_audit.py` recomputes all
  of it — event chain, every attested row, every `form_answers` hash, every stored file's hash —
  and reports `LEDGER OK (...)` or every problem found.
- **Model calls** (`llm.call(stage, prompt_name, variables, job_id=...)`) run `omp -p --mode json
  --model <stage's model> --no-tools --no-session ...` as a subprocess, record the prompt
  template's hash (prompt version), the full rendered input, the raw event stream, tokens, cost,
  and — critically — the model that **actually** answered after any provider fallback, not just
  the one requested (a provider 429 can silently hand a call to a different model in plain-text
  mode). Each stage in `config.yaml` declares a `min_rank`; an answer from a model ranked below
  that is recorded but returned as a failure, so a weak fallback can never silently pass a strong
  gate (e.g. the `auditor` stage requires rank 3).
- **Tiered models, code-checked.** A small model only quotes the job description verbatim
  (code-verified substring match) or points at an existing fact id / bank entry (code-verified
  against the real set) — never authors a value that reaches a CV or a form. A mid model drafts
  prose; a strong model, always a *different* model from the drafter, adversarially audits it
  against `profile/facts.yaml` before anything renders or is answered.
- **Answer bank** (`answer_bank` + `question_queue`): a form question queues once; the operator
  (or an audited model draft) answers it once at `global`/`company`/`job` scope
  (`pipeline/run/answer_question.py`); every future matching question resolves automatically.
  Lookup precedence is job > company > global. `answer_bank.json` (exported for the Node side) and
  every lookup/alias/retirement is itself an attested, hash-chained record.
- **Pre-submit capture**: immediately before clicking submit (and at the end of a dry run),
  `apply.mjs` snapshots *every* control on the form, not only the ones it filled — an ATS-
  autofilled value must be verifiable against facts/answers or the attempt is blocked; a required
  field left untouched blocks; nothing is ever submitted on a blocked gate. Full-page screenshots
  before submit and after confirmation are stored the same way as every other file.

## Browser rules (any agent touching the browser)
**Automated apply (`pipeline/apply/runner.mjs`, driven by `batch.py`)** connects to the operator's
own Chromium-based browser via `puppeteer-core` over CDP (`http://127.0.0.1:<port>`) and takes the
exclusive `pipeline/data/browser.lock` for the duration — refuses to start if another process holds
it, never force-closes the browser, opens exactly one new page, and `page.close()`s only that page
when done (`browser.close()` must never be called — it would kill the operator's everyday browser).
**Sequential access only** — two processes driving the browser at once can collide on the same
form. Only one process may drive the browser at a time; never create accounts or passwords;
never enter national ID numbers or government IDs; never submit anything unless explicitly told to.
